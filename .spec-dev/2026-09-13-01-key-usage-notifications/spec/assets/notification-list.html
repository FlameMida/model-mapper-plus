问题一：测试发送入口放哪？

spec 口径：test-send 显式发送「当前已保存」的通知；抽屉里编辑中的草稿要先用「预览」验证、保存后才能测试。

A

列表行内按钮（mockup 当前形态）

针对已保存通知，语义最干净；入口直接可见。

B

抽屉 footer

编辑时顺手，但容易和「预览」混淆；草稿未保存时需要禁用并解释，多一层状态。

C

两处都有

行内发已保存版，抽屉 footer 发已保存版（草稿时禁用+提示先保存）。方便但入口重复。

问题二：投递记录（GET /notifications/deliveries）在哪看？

A

列表行展开（Table expand 行）

该通知的投递记录内联展开：时间、平台、周期、状态、合并次数；贴近列表语境。

B

编辑抽屉加第三个 Tab「投递记录」

与模板、平台配置并列；但「查看记录」要进「编辑」入口，语义有点绕。

C

面板级独立查询区

Key 管理页新开一块投递查询（按 Key/通知/平台/状态筛选），发挥 deliveries 查询接口的全部能力；适合排查全局问题，离单条通知稍远。
